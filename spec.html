App Bundle Layout Specification

Version 1.0

A filesystem convention for self-contained applications. An app is one directory. Copying it is installation; deleting it is uninstallation. The same layout applies to desktop apps, command-line tools, and daemons, at user or system scope.

1. App root

Every app has exactly one root directory. Everything the app reads or writes lives inside it, except where a supervisor relocates an individual mutable directory (§3.4).

1.1 Scope

ScopeApp rootOwner
Per-user~/.apps/<id>/the user
System/opt/apps/<id>/root or a dedicated service user
  • The internal layout (§1.2) is identical at both scopes.
  • Base paths are overridable: $APP_HOME replaces ~/.apps, $APP_SYSTEM_HOME replaces /opt/apps. The <id> segment and the internal layout are unchanged.
  • A system-scope app MUST NOT write into any user's ~/.apps/. A per-user app MUST NOT write into /opt/apps/.
  • Scope is declared, not inferred. See §3.

1.2 Internal layout

<app-root>/ ├── app.toml # manifest (required); describes the root ├── program/ # immutable tree (required); replaced wholesale on upgrade │ ├── bin/ # executed or exposed files (convention) │ ├── lib/ # libraries and app code (convention) │ └── resources/ # read-only assets (convention) ├── data/ # persistent mutable data ├── cache/ # regenerable data └── run/ # ephemeral; cleared or ignored on startup

program/'s interior is a convention, not a requirement. Only two structural facts are normative: entry (from app.toml) MUST resolve to an executable file inside program/, and nothing in program/ is written at runtime. A bundle with program/bin/foo and nothing else conforms. The bin/, lib/, resources/ split is the recommended shape for bundles that need it.

  • app.toml is at the root because it describes the root. It is replaced on upgrade (§8) and is never written at runtime.
  • program/ is the tree that ships. It is never modified at runtime.
  • data/, cache/, and run/ are created by the app on first use.
  • The app MUST NOT write anywhere outside program/ (which it may not write at all) and the three mutable directories.

1.3 Modes

PathPer-userSystem
root07000750, owned by the service user

If clients outside the service group must reach a socket in run/, set the root to 0751 (traverse-only) and run/ to 0755. A 0755 run/ under a 0750 root is unreachable and therefore an error.

2. Manifest (app.toml)

TOML, at the app root. Unknown keys are ignored. All paths in the manifest are relative to the tree root (program/), regardless of the manifest's own location. Absolute paths are invalid.

2.1 Required fields

FieldTypeDescription
idstringUnique identifier (§2.3). Stable across versions. Names the app root.
namestringHuman-readable name.
versionstringVersion string. Opaque to this specification.
entrystringPath to the executable, relative to program/. MUST resolve to an executable file. MUST be a foreground process.

2.2 Optional fields

FieldTypeDescription
iconstringPath to an icon, relative to program/.
descriptionstringShort description.
licensestringSPDX license identifier.
homepagestringURL.
scopestring"user" or "system". The intended installation scope. Installers SHOULD warn when installing at a different scope. Does not affect runtime resolution (§3).
[mime]tablehandles = ["type/subtype", ...] — file types the app opens.

2.3 Identity (id)

  • MUST be lowercase, dot-separated, at least two segments, and filesystem-safe: a–z, 0–9, ., -, _. No /, no spaces, no leading ., no .., no empty segment.
  • SHOULD be a namespace the author controls: a domain in reverse-DNS (org.example.monitord) or a platform handle (github.alice.jsonfmt).
  • MUST be stable across versions. Changing it orphans the app root and all its data.
  • id is self-asserted and unverified. It is a namespace for paths and display, not an identity or authorization claim. Conventions reduce collisions; they do not prevent them. Hosts and installers MUST NOT treat id as proof of authorship.

2.4 Examples

id = "org.example.notepad"
name = "Notepad"
version = "1.2.0"
entry = "bin/notepad"
icon = "resources/icon.svg"
scope = "user"
id = "org.example.monitord"
name = "monitord"
version = "0.4.2"
entry = "bin/monitord"
scope = "system"

The format does not distinguish app types. Desktop apps, command-line tools, and daemons use the same manifest and the same layout. How entry is run — interactively, supervised, socket-activated — is outside this specification.

entry may be a native executable, a script with an interpreter directive, or a launcher that sets up an interpreted runtime and execs the interpreter. The manifest does not distinguish these; the launcher is the sanctioned mechanism (§7.3).

3. Runtime path resolution

  1. If $APP_ROOT is set and non-empty, it is the app root. The app MUST resolve symlinks and use the real path.
  2. Otherwise, scope selects the base:
    • $APP_SCOPE=system → $APP_SYSTEM_HOME or /opt/apps
    • $APP_SCOPE=user, or unset → $APP_HOME or ~/.apps
    The app root is <base>/<id>/.
  3. The tree root is <app-root>/program/. The manifest is <app-root>/app.toml. All asset access goes through the tree root: resources/<path> is reached as tree_root()/resources/<path>.
  4. Each mutable directory MAY be relocated individually by $APP_DATA_DIR, $APP_CACHE_DIR, and $APP_RUN_DIR (absolute paths). Unset means inside the app root. This exists for supervisors that mandate /var/lib/<id>, /var/cache/<id>, and /run/<id>. When used, the app treats them as its mutable directories; the installer MUST also remove them on purge.

Scope is declared, never inferred from credentials. An app MUST NOT use the effective UID to decide between user and system roots. System-scope apps SHOULD be launched through a wrapper that sets $APP_ROOT, or by a supervisor that sets $APP_SCOPE=system; a generated unit file that sets either is sufficient. Apps SHOULD fail with a clear message if neither is set and the root cannot be determined unambiguously.

Apps MUST resolve symlinks before deriving the root, so a symlinked entry point still finds the real tree. A build that bakes in an absolute install prefix is non-conforming.

4. Mutable directories

PurposePathLifetimeSafe to delete
Data<app-root>/data/permanentno (loses user data)
Cache<app-root>/cache/until cleanedyes (loses time only)
Run<app-root>/run/process/sessionyes (dead already)

The three directories are the complete set of roles that mutable data can play, on two axes:

RegenerableNot regenerable
Session-scopedrun/— (incoherent)
Cross-sessioncache/data/

The fourth quadrant is empty by definition: anything that must survive a restart and cannot be rebuilt is cross-session, not session-scoped. Three directories is therefore the minimum, and no one of them can be removed without collapsing an axis.

  • The app creates these on first use. An app that needs only data/ is conforming and never creates the other two.
  • run/ MUST be cleared or ignored on every startup, so its persistence across reboot is irrelevant. Supervisors that remove it on stop (e.g. systemd's RuntimeDirectory=) provide a stronger guarantee; apps MUST NOT depend on that.
  • data/ survives reboot, logout, crashes, and upgrades. It is removed only on explicit purge. Its internal structure is the app's own and is opaque to everything else.
  • cache/ may be deleted at any time without loss of user data. Its internal structure is the app's own.

What data/ is. It holds everything the app persists: settings, local databases, indexes, tokens, history, and any files whose lifecycle the app owns. It is the app's durable state, and it is the reason uninstall has two modes (remove keeps it; remove --purge does not).

It is not a general-purpose home for user documents. An app that manages files the user considers theirs (notes, projects, photos) SHOULD store them where the user chooses, or in a location the user can find and open with other tools. Files in data/ are expected to be backed up and restored with the app root, not browsed by the user.

5. In-code convention

Apps SHOULD centralize path logic in one small module:

  • app_root() — per §3.
  • tree_root() — app_root()/program/.
  • resource(path) — tree_root()/resources/<path>.
  • data_dir(), cache_dir(), run_dir() — per §4, created on demand.

Rules:

  • id is a single constant, or generated from app.toml at build time. One source of truth.
  • All asset access goes through resource(). All writes go through the three mutable directories.
  • Apps MUST NOT hardcode ~/.<name>, ~/.<id>, or XDG paths.
  • entry runs in the foreground. Apps MUST NOT self-daemonize (no fork/setsid/double-fork).

Reference modules per language: Appendix A.

6. Packaging

  • Output tree: a build command (conventionally make bundle) produces build/<id>/ containing app.toml and program/, conforming to §1.2 and §2.
  • Source tree is unconstrained. The specification says nothing about source layout. Each project's bundle target maps its own sources into build/<id>/. Templates: Appendix B.
  • Archive: canonical .tar.gz (.zip allowed) whose root contains exactly one directory named <id>/, itself containing app.toml and program/. No install scripts, no post-install hooks, no build-time absolute prefixes.
  • Dependencies are resolved at build time and shipped flat inside program/. A bundle MUST NOT resolve its dependencies at runtime, and MUST NOT ship a runtime environment (venv, gem home, node_modules tree with absolute links) that bakes in absolute paths.
  • Dev runs the assembled tree. The dev command (conventionally make dev) runs bundle, then creates a temporary root with program/ symlinked to the build tree and fresh mutable directories, and executes program/bin/<entry> with APP_ROOT pointing at it, so the paths exercised in development are the paths that ship.

7. Installation

A conforming installer extracts a verified archive to the scope's app root and exposes entry.

ScopeApp rootEntry exposed as
Per-user~/.apps/<id>/~/.local/bin/<entry-name> symlink or wrapper
System/opt/apps/<id>//usr/local/bin/<entry-name> symlink or wrapper
  • The installer MUST verify the archive conforms before extraction: exactly one <id>/ at the archive root, <id>/app.toml present with valid required fields, <id>/program/<entry> an executable file.
  • Extraction MUST be atomic: unpack to a temp directory under the target parent, then rename() into place.
  • The installer MUST preserve executable bits and symlinks.
  • The installer MUST refuse to overwrite an existing <id> unless --force, and SHOULD warn when the existing manifest's name or entry differs from the new one.
  • The installer MUST refuse to install a bundle whose scope differs from the target scope unless an explicit flag is given.
  • There are no install-time scripts. First-run setup is the app's job.
  • Uninstall removes program/, cache/, and run/. data/ is removed only with explicit purge.
  • Menu entries and MIME registration are out of scope. Hosts MAY derive them from app.toml; nothing requires it.

7.1 Exposure

The exposed entry may be a symlink to program/<entry> or a wrapper script that sets APP_ROOT and execs it. For a native executable, a symlink is sufficient. For an interpreted app, a wrapper is required (§7.3). At system scope, the exposed entry SHOULD be a wrapper that sets $APP_ROOT explicitly, so resolution never depends on the caller's environment.

7.2 What the installer does not do

It does not parse state, run app code, register services, restart daemons, or touch anything outside <app-root> and the exposure directory. Its entire job is: verify, extract, swap, link.

7.3 Launchers

An interpreted app ships a launcher at entry. The launcher is a script with an interpreter directive, owned by the app, and is responsible for:

  • deriving APP_ROOT from its own resolved path when it is not already set;
  • putting program/lib/ on the runtime's search path;
  • redirecting any runtime bytecode or compilation cache into cache/;
  • execing the interpreter so the process is the app, not a shell parent.

The launcher is the only file that must be executable in an interpreted bundle. See Appendix B for examples.

8. Upgrading

An upgrade replaces program/ and app.toml and MUST NOT modify data/, cache/, or run/.

8.1 Procedure

  1. Verify the new archive conforms (§7).
  2. Extract to <app-root>/.staging-<id>/ — same filesystem as the root, so each swap is atomic.
  3. Swap the tree:
    • rename(<app-root>/program, <app-root>/.old-program)
    • rename(<app-root>/.staging-<id>/program, <app-root>/program)
    Where available, renameat2(RENAME_EXCHANGE) performs this in one step and is preferred.
  4. Replace the manifest atomically: write the new app.toml to a temporary file in the app root, then rename() it over the old one.
  5. Delete .old-program on success. If the second tree rename fails, restore .old-program → program/.
  6. Update the exposure symlink or wrapper if the entry name changed.

A partially-extracted tree MUST never be visible as program/.

8.2 Rules

  • The installer MUST refuse to upgrade across a scope change (user ↔ system) without an explicit flag.
  • The installer MUST refuse to upgrade when the new manifest's id differs from the directory name.
  • The installer MUST refuse to upgrade when the archive's signature is present and invalid. When the archive is unsigned, it SHOULD warn.
  • The installer MUST NOT touch data/, cache/, or run/. Data migration is the app's responsibility.
  • The installer MUST NOT restart daemons. Daemons pick up the new tree when supervision restarts them.

8.3 Data migration

Apps that persist structured data MUST maintain a migration path, and SHOULD record a schema version marker in data/ (conventionally data/version).

  • On startup, the app compares the marker against the version its code expects and migrates forward if needed.
  • Downgrade safety is the app's responsibility: it detects too-new data via the marker and either migrates backward or refuses to start with a clear message.
  • The installer never interprets data/.

8.4 Running processes

  • Native executables. On Linux, rename() over a running executable's path is safe: the running process keeps the old inode until it exits. New launches get the new tree, and .old-program can be removed immediately.
  • Interpreted apps. The old-inode guarantee does not apply. A running interpreter reads program/ lazily, so an upgrade during execution can mix old in-memory code with new files on disk. Upgrading a running interpreted app is unsafe. Interactive apps SHOULD detect that their tree changed (for example, by comparing a build identifier recorded at startup) and refuse to continue or offer to restart. Apps that cannot do this MUST be upgraded only while not running.
  • Daemons. The installer leaves the new tree in place and lets supervision restart the service on its own schedule. Restarts remain under the administrator's control.

8.5 Rollback

  • Automatic rollback on swap failure: .old-program is restored to program/.
  • Manual rollback: --keep N retains up to N previous trees as .old-program-N. Off by default.
  • Data rollback is the app's problem, signalled by the schema marker (§8.3).

9. Daemons

A daemon is an app whose entry runs as a long-lived foreground process. It uses the same layout as any other app.

  • A system-scope daemon lives at /opt/apps/<id>/, owned by root or a dedicated service user. Its data/, cache/, and run/ are inside that root, owned accordingly. It MUST NOT write into any user's ~/.apps/.
  • A per-user daemon lives at ~/.apps/<id>/, owned by the user, with its mutable directories inside. It MUST NOT write into /opt/apps/.
  • Supervision (systemd, launchd, a process manager, or a user running it in a terminal) is out of scope. The spec guarantees only that entry is a foreground process rooted at the app root.
  • Socket and lock paths are <app-root>/run/. Clients find them by the same resolution rules (§3).
  • A daemon MUST unlink a stale socket before binding. run/ may be cleared on startup, but an app that cannot rely on that MUST check for an existing socket path and remove it after verifying no process is listening. run/ being emptied by the supervisor is an optimization, not the correctness mechanism.
  • A daemon MUST NOT assume run/ survives a restart. Its durable configuration belongs in data/.

10. Relationship to other formats

  • macOS .app. Closest structural analogue: Contents/ ≈ program/, Info.plist ≈ app.toml, CFBundleIdentifier ≈ id. macOS keeps mutable data outside the bundle (~/Library/Application Support/<id>/, ~/Library/Caches/<id>/) because the bundle is code-signed and the seal covers Contents/. This format internalizes mutable data because the root, not the bundle, is the unit: the point is that deleting the root is a complete uninstall. macOS's externalization is why uninstalling a Mac app leaves a dozen directories behind.
  • FHS / Debian / RPM. These install a diff against / and bake absolute paths at build time, scattering an app across /usr, /etc, /var/lib, /run. This format gives each app a single root with the same internal shape at every scope. A system package MAY wrap a conforming app by extracting it intact to /opt/apps/<id>/; it MUST NOT split the tree across FHS directories. Where a supervisor mandates FHS placement for mutable data, §3.4's per-directory overrides express it.
  • systemd's StateDirectory=, CacheDirectory=, RuntimeDirectory=. The same three roles, externally managed. A generated unit file can express this layout in four lines, and under ProtectSystem=strict those directives are also the write whitelist. This is the strongest external argument for the taxonomy. Note that RuntimeDirectory= is removed on stop, which is stronger than "cleared on startup."
  • Homebrew. A keg is the closest structural match to program/, but keg state lives in a shared prefix var/, which is why uninstall leaves data behind and needs per-formula cleanup stanzas. Homebrew also patches absolute paths at install time; this format requires no patching because resolution is runtime-relative.
  • Nix. A store path is the purest immutable-tree model, and generation symlinks are a cleaner atomic-swap mechanism than the two-rename() procedure here. Nix bakes absolute store paths into binaries, which is what makes trees non-relocatable; this format goes the other way and forbids baked prefixes.
  • Containers and sandbox packages. macOS/iOS app containers, Android's per-package /data/data/<pkg>/, and Windows MSIX package containers all internalize mutable data and enforce the root as a unit. They enforce it with the kernel; this format enforces it with convention (§12.2).
  • Flatpak / Snap / AppImage. Runtimes with sandboxing and their own integration conventions. This format is layout only.

11. What this specification does not define

  • The interior of program/ and data/. Both are opaque to everything but the app. Tools MUST NOT depend on internal structure. The bin/, lib/, resources/ split is a recommendation.
  • Domain. This format targets apps that are more than a single static binary: apps with resources too large to embed, apps that ship a language runtime or interpreter, apps with several files, and daemons. A self-contained single-file tool needs none of this and is out of scope.
  • The language runtime. Either bundled under program/ or assumed present on PATH. The spec does not prescribe which; it requires only that the bundle resolve and run without absolute install prefixes.
  • Runtime version constraints. The launcher checks and fails with a clear message. Not a manifest field.
  • Multi-command tools. A bundle exposes one entry. Tools with subcommands ship their commands under program/bin/ and dispatch from the entry, or expose the primary command. A first-class commands table is not defined here.
  • Library-only packages. Not apps; out of scope.
  • Migration from conventional layouts (~/.<name>, XDG directories). Out of scope for this specification. A conforming installer MAY offer an adoption command; if it does, it MUST NOT leave the old location as a live fallback in steady state.
  • Menu entries, icon themes, MIME registration, sandboxing, supervision, autostart, or updates beyond §8.
  • Daemon lifecycle beyond "entry is a foreground process."
  • Signing, dependency resolution, or repositories.
  • Source tree layout.

12. Conformance

12.1 An app

An app conforms if:

  1. Its root matches §1.1 and contains app.toml and program/ per §1.2.
  2. Its app.toml contains the required fields of §2 with valid values, and id satisfies §2.3.
  3. Its entry resolves to an executable file inside program/.
  4. It resolves paths per §3 and uses storage per §4.
  5. Its entry runs in the foreground and does not self-daemonize.
  6. It writes only inside its mutable directories.

12.2 The isolation test

Run the app with APP_ROOT set to a fresh empty directory and HOME set to a second fresh empty directory. After a normal run, $HOME MUST still be empty. This is the mechanical statement of "the app writes nowhere outside its root" and the test that catches the ~/.<name> habit.

12.3 Other conformance

An installer conforms if it satisfies §7 and §8. A packaging command conforms if its output satisfies §6.

Appendix A — Reference path modules

These are examples, not normative. They implement §3 and §4.

Python

import os
import pathlib

ID = "org.example.notepad"          # single source of truth


def app_root() -> pathlib.Path:
    if r := os.environ.get("APP_ROOT"):
        return pathlib.Path(r).resolve()
    if os.environ.get("APP_SCOPE") == "system":
        base = os.environ.get("APP_SYSTEM_HOME") or "/opt/apps"
    else:
        base = os.environ.get("APP_HOME") or str(pathlib.Path.home() / ".apps")
    return (pathlib.Path(base) / ID).resolve()


def tree_root() -> pathlib.Path:
    return app_root() / "program"


def resource(*p: str) -> pathlib.Path:
    return tree_root() / "resources" / pathlib.Path(*p)


def _dir(env: str, default: str) -> pathlib.Path:
    d = pathlib.Path(os.environ.get(env) or (app_root() / default))
    d.mkdir(parents=True, exist_ok=True)
    return d


def run_dir()   -> pathlib.Path: return _dir("APP_RUN_DIR", "run")
def data_dir()  -> pathlib.Path: return _dir("APP_DATA_DIR", "data")
def cache_dir() -> pathlib.Path: return _dir("APP_CACHE_DIR", "cache")

Rust

use std::path::PathBuf;

const ID: &str = "org.example.notepad";

pub fn app_root() -> PathBuf {
    if let Some(r) = std::env::var_os("APP_ROOT") {
        return PathBuf::from(r);
    }
    let base = if std::env::var("APP_SCOPE").as_deref() == Ok("system") {
        std::env::var_os("APP_SYSTEM_HOME")
            .map(PathBuf::from)
            .unwrap_or_else(|| PathBuf::from("/opt/apps"))
    } else {
        std::env::var_os("APP_HOME")
            .map(PathBuf::from)
            .unwrap_or_else(|| {
                PathBuf::from(std::env::var_os("HOME").unwrap()).join(".apps")
            })
    };
    base.join(ID)
}

pub fn tree_root() -> PathBuf { app_root().join("program") }
pub fn resource(p: &str) -> PathBuf { tree_root().join("resources").join(p) }

fn dir(env: &str, default: &str) -> PathBuf {
    let d = std::env::var_os(env)
        .map(PathBuf::from)
        .unwrap_or_else(|| app_root().join(default));
    let _ = std::fs::create_dir_all(&d);
    d
}

pub fn run_dir()   -> PathBuf { dir("APP_RUN_DIR", "run") }
pub fn data_dir()  -> PathBuf { dir("APP_DATA_DIR", "data") }
pub fn cache_dir() -> PathBuf { dir("APP_CACHE_DIR", "cache") }

Go

package paths

import (
	"os"
	"path/filepath"
)

const ID = "org.example.notepad"

func appRoot() string {
	if r := os.Getenv("APP_ROOT"); r != "" {
		abs, _ := filepath.Abs(r)
		return abs
	}
	var base string
	if os.Getenv("APP_SCOPE") == "system" {
		base = os.Getenv("APP_SYSTEM_HOME")
		if base == "" {
			base = "/opt/apps"
		}
	} else {
		base = os.Getenv("APP_HOME")
		if base == "" {
			home, _ := os.UserHomeDir()
			base = filepath.Join(home, ".apps")
		}
	}
	return filepath.Join(base, ID)
}

func treeRoot() string         { return filepath.Join(appRoot(), "program") }
func resource(p string) string { return filepath.Join(treeRoot(), "resources", p) }

func dir(env, def string) string {
	d := os.Getenv(env)
	if d == "" {
		d = filepath.Join(appRoot(), def)
	}
	os.MkdirAll(d, 0o700)
	return d
}

func runDir() string   { return dir("APP_RUN_DIR", "run") }
func dataDir() string  { return dir("APP_DATA_DIR", "data") }
func cacheDir() string { return dir("APP_CACHE_DIR", "cache") }

Appendix B — Bundle templates

Python

Launcher at program/bin/notepad (shipped as scripts/launcher.sh):

#!/bin/sh
set -eu

# Resolve through symlinks to the real tree, then up to the app root.
self=$(readlink -f "$0")
tree=$(dirname "$(dirname "$self")")   # <root>/program
root=$(dirname "$tree")                # <root>

export APP_ROOT="${APP_ROOT:-$root}"
export PYTHONPATH="$tree/lib${PYTHONPATH:+:$PYTHONPATH}"
export PYTHONPYCACHEPREFIX="$root/cache/pyc"
mkdir -p "$root/cache"

exec python3 -m notepad "$@"

Makefile:

ID := org.example.notepad

bundle:
	rm -rf build/$(ID)
	mkdir -p build/$(ID)/program/bin build/$(ID)/program/lib build/$(ID)/program/resources
	cp -r src/notepad build/$(ID)/program/lib/
	cp -r assets/. build/$(ID)/program/resources/
	install -m 0755 scripts/launcher.sh build/$(ID)/program/bin/notepad
	cp app.toml build/$(ID)/app.toml
	find build/$(ID)/program -name __pycache__ -prune -exec rm -rf {} +

dev: bundle
	./scripts/run-dev.sh build/$(ID)

run-dev.sh creates a temporary root with program/ symlinked to the build tree and fresh mutable directories, then runs:

#!/bin/sh
set -eu
build=$(readlink -f "$1")
tmp=$(mktemp -d)
ln -s "$build/program" "$tmp/program"
mkdir -p "$tmp/data" "$tmp/cache" "$tmp/run"
trap 'rm -rf "$tmp"' EXIT INT TERM
APP_ROOT="$tmp" exec "$build/program/bin/notepad" "$@"

Appendix C — Reference installer

#!/bin/sh
# appctl install|upgrade|remove|list|run
#        [--user|--system] [--force] [--purge] <arg>
set -eu

scope_root() {
  case "$1" in
    --system) echo "${APP_SYSTEM_HOME:-/opt/apps}" ;;
    *)        echo "${APP_HOME:-$HOME/.apps}" ;;
  esac
}

bindir_for() {
  case "$1" in
    --system) echo "/usr/local/bin" ;;
    *)        echo "$HOME/.local/bin" ;;
  esac
}

# Minimal TOML reader: finds `key = "value"` or `key = 'value'`.
field() {
  key="$2"; file="$1"
  sed -n "s/^[[:space:]]*${key}[[:space:]]*=[[:space:]]*\"\([^\"]*\)\".*/\1/p;
          s/^[[:space:]]*${key}[[:space:]]*=[[:space:]]*'\([^']*\)'.*/\1/p" \
    "$file" | head -n1
}

cmd="$1"; shift

case "$cmd" in

install|upgrade)
  scope="--user"; force=0
  while [ $# -gt 0 ]; do case "$1" in
    --user|--system) scope="$1" ;;
    --force) force=1 ;;
    *) break ;;
  esac; shift; done
  archive="$1"

  root="$(scope_root "$scope")"
  bindir="$(bindir_for "$scope")"
  staging="$root/.staging-$$"
  trap 'rm -rf "$staging"' EXIT INT TERM

  mkdir -p "$staging" "$bindir"
  tar -xzf "$archive" -C "$staging" --strip-components=1

  id="$(field "$staging/app.toml" id)"
  entry="$(field "$staging/app.toml" entry)"
  [ -n "$id" ] || { echo "not conforming: missing id" >&2; exit 1; }
  [ -n "$entry" ] || { echo "not conforming: missing entry" >&2; exit 1; }
  [ -x "$staging/program/$entry" ] || {
    echo "not conforming: program/$entry is not executable" >&2; exit 1; }

  dest="$root/$id"
  if [ -e "$dest" ] && [ "$cmd" = "install" ] && [ "$force" -eq 0 ]; then
    echo "exists: $id (use --force or upgrade)" >&2; exit 1
  fi

  mkdir -p "$dest"
  [ -e "$dest/program" ] && mv "$dest/program" "$dest/.old-program"

  mv "$staging/program" "$dest/program"
  tmp="$dest/.app.toml.$$"
  cp "$staging/app.toml" "$tmp"
  mv "$tmp" "$dest/app.toml"

  [ -e "$dest/.old-program" ] && rm -rf "$dest/.old-program"

  ln -sfn "$dest/program/$entry" "$bindir/$(basename "$entry")"
  echo "installed: $id -> $dest"
  ;;

remove)
  scope="--user"; purge=0
  while [ $# -gt 0 ]; do case "$1" in
    --user|--system) scope="$1" ;;
    --purge) purge=1 ;;
    *) break ;;
  esac; shift; done
  id="$1"
  root="$(scope_root "$scope")"
  bindir="$(bindir_for "$scope")"
  dest="$root/$id"
  [ -f "$dest/app.toml" ] || { echo "not installed: $id" >&2; exit 1; }

  entry="$(field "$dest/app.toml" entry)"
  [ -n "$entry" ] && rm -f "$bindir/$(basename "$entry")"

  if [ "$purge" -eq 1 ]; then
    rm -rf "$dest"
  else
    rm -rf "$dest/program" "$dest/cache" "$dest/run"
  fi
  echo "removed: $id"
  ;;

list)
  scope="--user"; [ "${1:-}" = "--system" ] && scope="--system"
  root="$(scope_root "$scope")"
  for d in "$root"/*/; do
    [ -f "$d/app.toml" ] && field "$d/app.toml" id
  done
  ;;

run)
  scope="--user"
  [ "${1:-}" = "--system" ] && { scope="--system"; shift; }
  id="$1"; shift
  root="$(scope_root "$scope")"
  dest="$root/$id"
  entry="$(field "$dest/app.toml" entry)"
  APP_ROOT="$dest" exec "$dest/program/$entry" "$@"
  ;;

*)
  echo "usage: appctl install|upgrade|remove|list|run" >&2
  exit 2
  ;;
esac

The field() reader is minimal on purpose: it handles quoted scalar values and nothing else. A conforming installer may use a real TOML parser, add zip support, warn on manifest mismatches, verify signatures, and preserve symlinks. The shape does not change: verify, extract, swap, link.
